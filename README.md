Описание решения

Поставленная задача
Нужно было по короткому запросу пользователя выбрать до 50 объявлений услуг из заданного корпуса. Это этап отбора кандидатов: дальше их могла бы упорядочить другая модель. Поэтому основной ориентир Recall@50, то есть доля выбранных пользователями объявлений, которые удалось включить в ответ. Порядок внутри итоговой пятидесятки на эту метрику не влияет.

Я использовала текстовый поиск по TF-IDF и объединила несколько списков кандидатов. Нейросетей, эмбеддингов и внешних API в этом решении нет. Основная идея - искать по заголовку и описанию отдельно, добавить совпадения по частям слов и учитывать локацию, сохранив при этом поиск по всему корпусу.

Данные и признаки

В итоговом запуске читаются два файла:

- benchmark_queries.parquet 2 452 запроса, для которых нужен ответ;
- benchmark_items.parquet 189 212 объявлений, среди которых идёт поиск.

В задании также есть train.parquet с 497 673 положительными парами «запрос - выбранное объявление». В текущем коде он не используется. Вызов fit здесь означает построение словаря и подсчёт статистики слов по корпусу объявлений, а не обучение на пользовательских выборах.

 search_query  Текст запроса, который преобразую в каждое из трёх TF-IDF представлений. 
 item_title_raw  Отдельные словный и символьный индексы. В заголовке обычно коротко названа услуга. 
 item_description_raw  Отдельный словный индекс: нужная услуга или уточнение могут быть только в описании. 
 search_location_id, item_location_id  Отбор объявлений с тем же ID локации в локальные списки кандидатов. 
 query_id, item_id  Связь исходных данных с ответом. Их содержимое не используется для оценки похожести. 

Поля с фильтрами запроса, параметры объявления, категории и подкатегории, цена, рейтинг, число отзывов, координаты, доставка и ограничения способов связи в итоговом алгоритме не используются. Я оставила решение на текстовых совпадениях и локации. Это упрощает схему, но означает, например, что фильтр «рейтинг от четырёх звёзд» явно не проверяется. Подтверждённого сравнения с добавлением этих признаков в папке нет, поэтому утверждать, что они бесполезны, нельзя.

Подготовка текста

Пропуски в текстовых полях заменяю пустой строкой. Затем привожу Unicode к NFKC, перевожу текст в нижний регистр, заменяю «ё» на «е» и убираю лишние пробелы. Так написание с разным регистром или буквой «ё» не создаёт лишних различий.

Как устроен поиск

Три представления текста

1. Слова заголовка. Использую отдельные слова и пары соседних слов: ngram_range=(1, 2). Одиночные слова дают совпадения по составляющим запроса, пары сохраняют часть информации о сочетании слов.
2. Слова описания. Те же настройки, но отдельные словарь и IDF. Так длинное описание не смешивается с заголовком в одном векторе и даёт самостоятельный список кандидатов.
3. Символьные фрагменты заголовка. Использую char_wb с длинами от 3 до 5 символов. Этот анализатор строит фрагменты внутри слов с дополнением пробелами у границ. Он может находить частичные совпадения при разных окончаниях и некоторых опечатках.

Для всех индексов min_df=2: признак должен встретиться минимум в двух объявлениях соответствующего поля. Это сокращает словарь, но может убрать полезную редкую модель устройства или название услуги. Частоту слова сглаживаю через 1 + log(tf), чтобы многократное повторение в описании не увеличивало его вес линейно. IDF уменьшает вес распространённых признаков.

Векторы нормируются по L2, поэтому их скалярное произведение даёт косинусную похожесть. Матрицы разреженные, веса хранятся в float32. Словарь строится по объявлениям; признаки запроса, которых в нём нет, игнорируются. Для словного индекса используется стандартный токенизатор scikit-learn с токенами длиной от двух символов.

Общий и локальный поиск

Для каждого представления получаю два списка глубиной до 50:

- Global: самые похожие объявления по всему корпусу.
- Local: самые похожие объявления с точным совпадением ID локации запроса.

Локальные кандидаты выбираются из всех найденных текстовых совпадений, а не из уже обрезанного общего top-50. Иначе подходящее местное объявление могло бы потеряться раньше, чем применится фильтр локации.

Общий список сохраняю, потому что жёсткое ограничение одной локацией для всех кандидатов могло бы исключать удалённые услуги или исполнителей из соседних мест. Расстояния по координатам, иерархия регионов и возможность выезда в коде не учитываются.

Тяжёлую операцию умножения разреженных матриц выполняю через CuPy на GPU. Запросы обрабатываются пакетами по 16, три индекса последовательно. Это ограничивает объём одновременно используемой памяти. Векторизация, отбор top-k и фильтрация по локации выполняются на CPU. При равных оценках раньше ставится объявление с меньшим номером строки корпуса.

Объединение шести списков

Порядок каналов зафиксирован:

1. слова заголовка, весь корпус;
2. слова описания, весь корпус;
3. слова заголовка, та же локация;
4. слова описания, та же локация;
5. символы заголовка, весь корпус;
6. символы заголовка, та же локация.

Объединяю их по кругу: первые позиции всех каналов, затем вторые и так далее, пока не наберётся 50 уникальных объявлений. Повторное объявление пропускаю. Это round-robin: оценки разных индексов не складываются, обученных весов каналов нет. Квота на канал не фиксирована, поскольку часть кандидатов повторяется или отсутствует.

Если совпадений мало, недостающие места не заполняются случайными объявлениями. Внутри массивов пустое место обозначено -1, при переводе в item_id такие значения удаляются. В сохранённом ответе для каждого запроса удалось получить 50 кандидатов.

Как проверялся результат перед отправкой

Здесь разделяю качество поиска и правильность файла: это разные проверки.

Проверка файла ответа

В коде ответ проверяется сначала до записи, затем повторно после чтения готового CSV. Проверяются:

- ровно две колонки query_id,answer, без колонки индекса;
- точное совпадение набора запросов с benchmark, без пропусков и повторов;
- длина query_id в 16 символов с сохранением исходного регистра;
- не больше 50 объявлений на запрос и отсутствие повторов внутри ответа;
- формат каждого item_id: 16 символов 0-9a-f;
- наличие каждого возвращённого объявления в корпусе.

В artifacts/submission_metrics.json сохранён отчёт запуска:

Таймер общего этапа в коде начинается после чтения данных и подготовки настроек. Поэтому это не полное время от запуска процесса. Отчёт также содержит размеры словарей, число ненулевых весов, среднее число кандидатов каждого канала и SHA-256 готового CSV. Хеш позволяет проверить, что отчёт относится к конкретному файлу.

Проверка Recall@50

Формула для одного запроса: число релевантных объявлений в ответе, делённое на число всех известных релевантных объявлений этого запроса. Затем значения усредняются по запросам, а не по отдельным парам.

В final_solution нет кода разбиения train на обучение и валидацию, расчёта Recall@50 на размеченной выборке, результатов сравнения каналов или оценки с платформы. Поэтому численное качество поиска здесь не указываю. Полные ответы из 50 ID и успешная проверка CSV сами по себе не подтверждают высокий Recall@50.

Для отдельной проверки качества можно было бы выделить группы запросов из train, собрать для каждого множество известных выбранных объявлений и измерить Recall@50 на заранее определённом корпусе. При использовании train для настройки важно не разносить один и тот же запрос с теми же условиями поиска между подбором параметров и итоговой проверкой. Также нужно явно учитывать, входят ли релевантные объявления в проверяемый корпус. Это описание возможной проверки, а не уже выполненного эксперимента.




После объединения у всех 2 452 запросов оказалось по 50 уникальных кандидатов. Значит, по заполненности списки дополнили друг друга. Насколько это улучшило полноту по релевантным объявлениям, без разметки установить нельзя.

Какие проблемы я учла в алгоритме

Возможная проблема  Что сделано в коде  Что остаётся ограничением 
Разный регистр, «ё»/«е», лишние пробелы  Одинаковая нормализация запросов и объявлений.  Синонимы и разные формулировки одной услуги так не объединяются. 
Окончания слов и опечатки мешают точному совпадению  Добавлен символьный поиск по заголовкам.  Частичные совпадения могут быть случайными; улучшение ecall отдельно не измерено. 
Услуга указана только в описании  Есть самостоятельный индекс описаний.  Длинное описание может перечислять много услуг и давать лишние совпадения. 
Текст подходит, но исполнитель из другой локации  Добавлены локальные каналы.  Global по-прежнему может включать дальние объявления, а соседние локации отдельно не учитываются. 
Жёсткий фильтр локации исключает подходящего исполнителя  Сохраняется общий поиск по всему корпусу.  Возможность удалённой работы или выезда явно не определяется. 
Одно объявление найдено несколькими каналами  При слиянии удаляются повторные индексы.  Два разных ID с одинаковым содержанием считаются разными объявлениями. 
Недостаточно текстовых совпадений  Используются несколько представлений; пустые позиции не превращаются в ID.  В другом наборе данных ответ может содержать меньше 50 кандидатов. 
Неверный формат ответа или чужой ID  Проверки перед записью и после чтения CSV.  Эти проверки ничего не говорят о релевантности. 

Файлы и воспроизведение

- build_answer.py  чтение данных, построение индексов, поиск, объединение и запись ответа.
- src/retrieval.py TF-IDF, выбор top-k, слияние каналов; также отдельные CPU-методы, которые финальный скрипт не вызывает.
- src/location_retrieval.py GPU-умножение и получение общего и локального списков.
- src/text.py нормализация и неиспользуемый в финальном запуске лемматизатор.
- src/validation.py проверки ответа.
- config.yaml параметры индексов, глубина поиска и размер пакета.
- requirements.txt зафиксированные зависимости.
- answer.csv сохранённый ответ.
- artifacts/submission_metrics.json статистика сохранённого запуска.

Используются открытые библиотеки scikit-learn для TF-IDF, SciPy для разреженных матриц, CuPy для GPU-операций, NumPy для обработки массивов, pandas и PyArrow для таблиц и Parquet, PyYAML для конфигурации. Готовые обученные модели не загружаются. После подготовки окружения обработка данных идёт локально, без внешних API.

Пример запуска из final_solution на машине с совместимой NVIDIA GPU и CUDA-окружением для cupy-cuda13x:

bash
python3 -m pip install -r requirements.txt
python3 build_answer.py --data-dir /path/to/data


Полный запуск перезапишет answer.csv и отчёт по путям по умолчанию; другие пути можно задать через --output и --metrics. Автоматического перехода на CPU нет. На текущем устройстве GPU-поиск при подготовке комментариев не запускался, совместимость окружения заново не проверялась.

Проверить уже готовый CSV можно без запуска GPU, если доступны исходные benchmark-файлы и CPU-зависимости:

bash
python3 build_answer.py --data-dir /path/to/data --validate-only


seed=42 сохраняется в отчёте, но случайной выборки или стохастического обучения в текущем алгоритме нет. Равные оценки разрешаются по номеру строки объявления, поэтому порядок корпуса тоже важен для воспроизведения.
